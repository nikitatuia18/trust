# Промт: сборка экрана из макета (черновик v1)

> Рабочая версия теперь — skill `/build-screen` (`.claude/skills/build-screen/SKILL.md`). Этот файл — исходный текст и список идей; правки вносить в skill.

Дизайн-система уже есть, поэтому макет — не источник компонентов, а источник логики и вида. Этот промт заменяет подход «собери по макету». Черновик: правим вместе, потом превращаем в команду `/build-screen`.

## Как пользоваться

Владелец пишет: ссылка на кадр + одна строка про смысл экрана («Account, раздел Affiliate»). Всё остальное ассистент делает по шагам ниже.

---

## Промт для ассистента

Ты собираешь экран из макета Figma в репозитории `trust`. Работай по-русски.

**Закон:** экран собирается только из компонентов `src/components` и токенов `src/styles`. Макет даёт логику (что делает экран, какие состояния) и вид (что где стоит). Состав компонентов макет не задаёт. Если макет и система расходятся — права система. Макет может быть тестовым: переменные в нём нерелевантны, опечатки возможны.

### Шаг 0. Прочитать (всегда, до макета)
1. `src/showcase/RulesPage.tsx` — правила системы.
2. `PLAN.md` и `docs/SCREEN-BUILD-ERRORS.md` — договорённости и прошлые ошибки.
3. `src/screens/SiteShell.tsx` и готовый экран рядом (`src/screens/registration/`) — как собирается каркас. Шапка, подвал, `PageLayout` берутся оттуда.
4. `src/components/index.ts` — что уже есть.

### Шаг 1. Разобрать макет
`get_metadata`, `get_design_context` (по частям, если кадр большой), скриншот. Для каждого блока записать: назначение, состояния, данные, действия.

### Шаг 2. Таблица соответствия (показать владельцу до кода, если есть хоть один пробел)
Для каждого блока макета:

| Блок макета | Компонент системы | Статус |
|---|---|---|
| … | Button secondary | есть |
| … | — | нет → предложение |

Статусы: **есть** (берём как есть), **ось** (у компонента есть такой вариант в Figma), **нет** (нужен новый компонент или решение владельца).

Запрещено молча:
- перерисовывать системный компонент по макету (шапка, кнопки, поля, иконки);
- добавлять/убирать блоки каркаса, которых нет (или есть) в системе;
- придумывать тексты, пункты меню, действия, статусы — ставь явную заглушку и вынеси в вопросы;
- копировать иконки-заглушки (дефолтная иконка Button) — подбери осмысленную из «06 — Icons» или спроси;
- расширять компонент осью, которой нет в Figma «03 — Components».

### Шаг 3. Недостающее
Нет компонента → сначала предложить владельцу: что это, где ещё пригодится, почему не подходят существующие. После согласия: токены (Figma «02 — Tokens» + `tools/raw`), компонент в Figma «03 — Components», код, витрина. Нельзя: сырые значения, примитивы, одноразовая верстка. Нет токена — завести или спросить.

### Шаг 4. Собрать
- Экран = папка `src/screens/<name>/`: типы и данные отдельно (`<name>Data.ts`), по файлу на блок, раскладка в `<name>.css` только на токенах.
- Контракт: данные и действия приходят props; колбэки `onXxx`; состояния загрузки и ошибки сервера предусмотрены.
- Страница `#/<name>`, запись во вкладке «Экраны».

### Шаг 5. Проверить (обязательно до отчёта)
1. `npm run build`.
2. Скриншот десктопа, сравнение с макетом блок за блоком.
3. Mobile 390px (iframe) и средняя ширина (~1100): нет горизонтального скролла, ничего не схлопывается.
4. Поиск сырых значений в новом CSS: `px` (кроме 0), `#hex`, `rgb(`, `--prim-`.
5. Если добавлялись компоненты — скриншот витрины «Компоненты».
6. Проход «каждый блок экрана → какой системный компонент» (из шага 2) — совпадает с кодом?

### Шаг 6. Отчёт (в таком порядке)
1. Ссылка на страницу.
2. **Вопросы к владельцу** (заглушки, иконки, тексты, пропуски в системе) — сверху, коротко.
3. Что добавлено в систему.
4. Отличия от макета (только осознанные, с причиной).
5. Что не проверено.

Коммит и пуш — сразу после проверки (договорённость владельца). Ошибки, найденные по ходу, дописать в `docs/SCREEN-BUILD-ERRORS.md`.

## Что можно оптимизировать (предложения, нужно решение)

1. **Команда `/build-screen`**: превратить этот промт в skill репозитория (`.claude/skills/build-screen/SKILL.md`). Тогда владелец пишет `/build-screen <ссылка>`, шаги 0–6 выполняются сами.
2. **Карта компонентов** (`docs/COMPONENT-MAP.md`): шаблоны макета → компонент («поле с подписью → TextField», «ряд вкладок → SegmentedControl», «меню из трёх точек → DropdownMenu»). Шаг 2 станет быстрым и без пробелов. Можно генерировать из `index.ts` и описаний компонентов.
3. **Автопроверка** `npm run check:screens`: ищет в `src/screens` сырые значения, `--prim-*`, импорты не из `components`, локальные стили с `color`/`background` вне токенов. Шаг 5.4 перестаёт зависеть от внимательности.
4. **Метки в Figma**: владелец помечает в макете «тестовый / боевой», а блоки, которых нет в системе, — стикером «нового компонента нет». Сокращает вопросы.
5. **Шаблон отчёта** — зафиксирован в шаге 6; можно сделать его формой.
6. **Library-режим**: заранее подготовить для разработчиков перечень «компонент → props», чтобы экран в коде и макет проверялись одним документом.
