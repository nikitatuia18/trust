Ты собираешь экран из макета Figma. Работай по-русски. Аргументы: `$ARGUMENTS` (ссылка на кадр + смысл экрана).

**Закон:** экран собирается только из `src/components` и `src/styles`. Макет даёт логику (состояния, действия) и вид (что где стоит), но не состав компонентов. Макет и система расходятся — права система. Макет может быть тестовым: переменные в нём нерелевантны, опечатки возможны.

## Шаг 0. Прочитать (до макета)
1. `src/showcase/RulesPage.tsx` — правила.
2. `docs/SCREEN-BUILD-ERRORS.md` — прошлые ошибки; `PLAN.md` — договорённости.
3. `src/screens/SiteShell.tsx` и готовый экран (`src/screens/registration/`, `src/screens/account/`) — каркас: шапка, подвал, `PageLayout` берутся оттуда.
4. `src/components/index.ts` — что уже есть. `docs/COMPONENT-MAP.md` (после `npm run map`) — шаблоны «макет → компонент», props, где используется: основа таблицы шага 2. Если компонент добавлялся после последнего `map` — перегенерировать.

## Шаг 1. Разобрать макет
`create_session` с fileKey из ссылки → `get_metadata`, `get_design_context` (скилл `skill://figma/figma-design-to-code/SKILL.md` грузится как MCP-ресурс; по частям, если кадр большой), `get_screenshot`. Для каждого блока: назначение, состояния, данные, действия. Метки владельца в кадре («тестовый», «нового компонента нет») учитывать.

## Шаг 2. Таблица соответствия
Для каждого блока макета: `Блок | Компонент системы | Статус`. Статусы: **есть**, **ось** (у компонента есть такой вариант), **нет** (нужен новый компонент или решение владельца). Если есть хоть один «нет» или сомнение — показать таблицу владельцу до кода.

Запрещено молча:
- перерисовывать системный компонент по макету (шапка, кнопки, поля, иконки);
- добавлять/убирать блоки каркаса;
- придумывать тексты, пункты меню, действия, статусы — явная заглушка + вопрос в отчёт;
- копировать иконки-заглушки из макета (дефолтная иконка Button) — подобрать из «06 — Icons» или спросить;
- расширять компонент осью, которой нет в Figma «03 — Components»;
- оставлять сырые значения (`180px`) — завести токен или спросить.

## Шаг 3. Недостающее
Нет компонента → сначала предложить владельцу: что это, где ещё пригодится, почему не подходят существующие. После согласия — skill `/new-component`.

## Шаг 4. Собрать
Папка `src/screens/<name>/`: данные отдельно (`<name>Data.ts`), по файлу на блок, раскладка в `<name>.css` только на токенах. Данные и действия — props, колбэки `onXxx`, состояния загрузки/ошибки сервера предусмотрены. Страница `#/<name>`, запись во вкладке «Экраны».

## Шаг 5. Проверить (обязательно до отчёта)
1. `npm run build`.
2. `npm run check` — сырые значения, `--prim-*`, несуществующие токены, импорты мимо `components`. Нарушение — исправить или вынести в вопросы.
3. `npm run shots -- <маршрут>` — PNG 1440 / 1100 / 390 в `.shots/`, переполнение скрипт считает сам. Открыть PNG, сравнить с макетом блок за блоком; на 390 ничего не схлопывается и не обрезано.
4. Если добавлялись компоненты — `npm run shots -- components` и посмотреть.
5. Проход «каждый блок экрана → какой системный компонент» совпадает с таблицей шага 2.

## Шаг 6. Отчёт (в таком порядке)
1. Ссылка на страницу.
2. **Вопросы к владельцу** (заглушки, иконки, тексты, пропуски в системе) — сверху, коротко.
3. Что добавлено в систему.
4. Отличия от макета (только осознанные, с причиной).
5. Что не проверено.

Коммит и пуш — сразу после проверки. Ошибки, найденные по ходу, дописать в `docs/SCREEN-BUILD-ERRORS.md`; повторившуюся — превратить в пункт этого skill.
